## 청킹 산출물 개요

본 프로젝트에서는 소비자분쟁 관련 기준·지침 데이터를 검색 정확도와 활용 목적에 맞게 차등 청킹하였다.</br>
아래 5개 파일은 모두 청킹이 완료된 최종 산출물이며, 각 파일은 서로 다른 사용 시나리오를 전제로 설계되었다.
</br>
("별표" 파일은 소비자분쟁해결기준 내의 분류)</br>
(별표 2는 작업 진행 중에 있음.)

### 1. 별표 1 – 대상 품목 분류

- 파일: table1_item_chunks.jsonl

#### 청킹 목적

- 사용자의 질의가 대부분 구체적인 품목명 단위로 발생

- 품목 분류표를 그대로 임베딩할 경우, 한 청크에 수십~수백 개 품목이 섞여 정밀도 저하

#### 청킹 방식

- items 필드를 품목 단위로 폭발(explode)

- 1 품목명 = 1 청크 구조

- 정규화, 동의어 보정, 괄호 불균형 등 전처리 완료

#### 사용 가이드

- VectorDB에서 품목 매칭 / 라우팅용 인덱스로 사용

- 별표 2·3·4와 사전 병합하지 않고, 런타임에서 2차 조회로 활용

### 2. 별표 3 – 보증기간 / 부품보유기간

- 파일: table3_warranty_chunks.jsonl

#### 청킹 목적

- 품목별 보증·보유 규칙이 길고 복합적인 구조

- 단순 1레코드=1청크는 검색 효율 저하

#### 청킹 방식

- 품목 단위 폭발(item_chunk) 기본

- 긴 항목은 parent (원문 앵커, 임베딩 제외), detail / rule (실제 임베딩 대상) 구조로 분리

- detail이 긴 경우 soft split 적용

#### 사용 가이드

- VectorDB 검색 대상: item_chunk, detail, rule

- parent는 원문 보존·출처 앵커 용도로만 사용

### 3. 별표 4 – 품목별 내용연수

- 파일: table4_lifespan_chunks.jsonl

#### 청킹 목적

- 내용연수 기준은 품목 리스트 + 설명 구조로 구성

- 품목 기준 검색 대응력을 확보하면서 원문 의미 유지 필요

#### 청킹 방식

- 원문 레코드는 유지

- item 필드에 포함된 품목 리스트를 분리하여 child 청크 생성

- 별표 1 품목 인덱스와 런타임 매칭 전제

#### 사용 가이드

- 단독 임베딩 + 필요 시 table1 기반 분류 정보 보강

- 수명/감가 관련 질의 대응에 사용

### 4. 전자거래 지침

- 파일: ecommerce_guideline_chunks.jsonl

#### 청킹 목적

- 법·지침 문서는 문맥 단위 이해가 중요

- 과도한 분할은 의미 손실 위험

#### 청킹 방식

- 의미 보존 중심 대청킹

- TARGET: 약 800~1600자

- HARD_MAX: 2400자

- 문단·조항 흐름을 최대한 유지

- path_hint는 헤딩 기반 요약 문자열로 제한

#### 사용 가이드

- 분쟁 판단이 아닌 사전 안내·주의사항 설명용

- 검색 결과는 요약/재진술에 적합

### 5. 콘텐츠이용자 보호지침

- 파일: content_guideline_chunks.jsonl

#### 청킹 목적

- 전자거래 지침과 동일하게 조항 간 맥락 유지가 핵심

- 예시·설명 조항이 혼재된 구조

#### 청킹 방식

- 전자거래 지침과 동일한 대청킹 전략 적용

- 조항 단위 의미 흐름 유지

- 과도한 초소형 청크 병합

#### 사용 가이드

- 콘텐츠/디지털 서비스 분쟁 사전 설명용

- “판단”이 아닌 참고 기준 제시 역할

### 정리 요약

- 별표 1: 품목 매칭 정확도 최우선 (라우팅용)

- 별표 3·4: 품목 + 규칙 설명 혼합 대응

- 지침 2종: 의미 보존 중심 안내용 문서

- 모든 파일은 역할 분리 + 런타임 결합을 전제로 설계됨

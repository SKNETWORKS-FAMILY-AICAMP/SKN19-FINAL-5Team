# PDF 파싱 방법 비교 분석

## 개요

소비자분쟁해결기준 PDF (37페이지)를 구조화된 JSON으로 파싱하기 위해 여러 방법을 시도한 결과를 비교 분석합니다.

---

## 시도한 파싱 방법

### 1. Google Gemini Vision API ✅ **성공**

**방법:**
```
PDF → 이미지 변환 → Gemini Vision API → JSON
```

**결과:**
- ✅ 전체 37페이지 파싱 완료
- ✅ 57개 표 감지
- ✅ 224개 분쟁항목 추출
- ✅ 비고 매핑 정확도 높음
- ✅ 계층 구조 완벽 보존

**파일:**
- 출력: `[별표 2] 품목별 해결기준 1.json` (209KB)

**소요 시간:**
- 약 40분 (페이지당 1초 + API 호출)

**예상 비용:**
- 약 $3-5 (Pay-as-you-go)

---

### 2. Azure Document Intelligence ❌ **실패**

**방법:**
```
PDF → Azure Layout Analysis → Markdown → Gemini → JSON
```

**결과:**
- ❌ 무료 티어(F0) 제한: 첫 2페이지만 분석
- 총 4개 표만 감지 (전체 57개 중)
- 21개 항목만 추출 (전체 224개 중)

**실패 원인:**
```
무료 티어 제약:
- 페이지 제한: 2페이지 (유료는 2,000페이지)
- 파일 크기: 4MB (유료는 500MB)
```

**해결 방법:**
- 유료 티어(S0)로 업그레이드 필요
- 하지만 Gemini가 이미 완벽하게 작동하므로 불필요

---

### 3. Upstage Solar DocVision ❌ **실패**

**시도한 방법:**
```python
client = OpenAI(
    api_key=UPSTAGE_API_KEY,
    base_url="https://api.upstage.ai/v1/solar"
)

response = client.chat.completions.create(
    model="solar-docvision",  # ❌ 잘못된 모델명
    messages=[...]
)
```

**오류 메시지:**
```
Error code: 400 - The requested model is invalid or no longer supported.
```

**실패 원인:**
- **"solar-docvision"은 비전 모델이 아님**
- 실제로는 **문서 임베딩 및 검색용 레거시 모델**
- Upstage는 Gemini/Claude처럼 **이미지를 직접 분석하는 멀티모달 비전 API를 제공하지 않음**

**Upstage 사용 가능 모델:**
- Solar Pro 2 (텍스트 LLM)
- Solar Mini (경량 LLM)
- Document Parse (PDF → HTML/Markdown)
- Information Extract (구조화된 데이터 추출)

### 4. Upstage Information Extraction ❌ **실패**

**시도한 방법:**
```python
client = OpenAI(
    api_key=UPSTAGE_API_KEY,
    base_url="https://api.upstage.ai/v1/information-extraction"
)

response = client.chat.completions.create(
    model="information-extract",
    messages=[...],
    response_format={
        "type": "json_schema",
        "json_schema": {
            "schema": {
                # 5단계 중첩 구조
                "tables": [
                    {
                        "items": [
                            {
                                "conditions": [
                                    {
                                        "sub_conditions": [
                                            {"notes": [...]}
                                        ]
                                    }
                                ]
                            }
                        ]
                    }
                ]
            }
        }
    }
)
```

**오류 메시지:**
```
Error code: 400 - Invalid Schema: The type of properties of object cannot be 'array' of 'object'.
```

**실패 원인:**
- **Upstage Information Extraction은 중첩된 배열 구조를 지원하지 않음**
- 우리 데이터 구조의 복잡도: 5단계 중첩
  ```
  tables[]
    → items[]
      → conditions[]
        → sub_conditions[]
          → notes[]
  ```

**Upstage JSON 스키마 제약:**
- ✅ 단순한 1-2단계 중첩만 지원
  ```json
  {
    "transactions": [
      {"date": "string", "amount": "number"}
    ]
  }
  ```
- ❌ 배열 안의 객체 안의 배열... 불가능
  ```json
  {
    "tables": [
      {
        "items": [
          {
            "conditions": [...]  // ← 너무 깊은 중첩
          }
        ]
      }
    ]
  }
  ```

### 5. Upstage Document Parse + Solar API ❌ **부정확**

**시도한 방법:**
```
PDF → Document Parse → HTML → Solar API → JSON
```

**결과:**
- HTML 변환은 성공
- 하지만 비고 매핑 부정확
- 계층 구조 손실

**실패 원인 상세 분석:**

#### 1️⃣ HTML 변환 시 시각적 정보 손실

**Document Parse가 생성하는 HTML:**
```html
<table>
  <tr>
    <td>분쟁유형</td>
    <td>해결기준</td>
    <td>비고</td>
  </tr>
  <tr>
    <td>1) 파종 전 불량 확인</td>
    <td>제품교환 또는 구입가 환급</td>
    <td rowspan="3">발아 불량은 종자 포장에...</td>
  </tr>
  <tr>
    <td>- 용량미달</td>
    <td>제품교환 또는 구입가 환급</td>
    <!-- 비고 셀 없음 (rowspan으로 병합됨) -->
  </tr>
</table>
```

**문제점:**
- `rowspan="3"` 속성은 있지만, **어떤 행들과 연결되는지** 명확하지 않음
- HTML 파서는 구조만 보존, **의미론적 연결 관계**는 손실
- 비고가 "1) 파종 전 불량 확인"과 연결되는지, 아니면 "- 용량미달"과 연결되는지 **Solar API가 추론해야 함**

#### 2️⃣ Solar API는 비전 모델이 아님

**Solar API의 한계:**
- **텍스트 기반 LLM**이므로 HTML 코드만 볼 수 있음
- **시각적 공간 관계**를 이해하지 못함
- 병합 셀이 어떻게 배치되어 있는지 **시각적으로 확인 불가**

**Gemini Vision과 비교:**

| 항목 | Gemini Vision | Solar API (HTML 입력) |
|------|--------------|---------------------|
| **입력** | 📸 이미지 (시각 정보) | 📄 HTML 텍스트 |
| **병합 셀 인식** | ✅ 시각적으로 직접 확인 | ❌ rowspan 속성만 봄 |
| **공간 관계** | ✅ 비고가 어느 행에 걸쳐있는지 직접 봄 | ❌ 추론으로만 파악 |
| **계층 구조** | ✅ 들여쓰기, 글꼴, 위치로 파악 | ❌ 텍스트 패턴으로만 추론 |

#### 3️⃣ 복잡한 표 구조의 애매모호성

**우리 문서의 복잡한 경우:**

```
┌─────────────────────┬──────────────────────┬─────────────────────┐
│ 1) 파종 후 불량     │ o 해결기준1          │  * 발아 불량은...   │ ← rowspan=5
│ - 재파종 가능 시    │ o 대파종자 교환      │  * 직접경비는...    │
│ - 재파종 불가능 시  │                      │  * 예상수익은...    │
│   ㆍ타품종 가능     │ o 차액 배상          │                     │
│   ㆍ타품종 불가능   │ o 예상수익액 배상    │                     │
└─────────────────────┴──────────────────────┴─────────────────────┘
```

**HTML로 변환하면:**
```html
<td rowspan="5">발아 불량은...<br>직접경비는...<br>예상수익은...</td>
```

**Solar API가 직면하는 문제:**
- "발아 불량"이라는 비고가 "파종 후 불량" 전체에 해당하는지?
- 아니면 특정 하위 조건에만 해당하는지?
- "직접경비"는 "재파종 가능 시"와 연결되는지?
- "예상수익"은 "타품종 가능/불가능" 둘 다와 연결되는지?

**→ HTML 텍스트만으로는 이런 매핑을 정확히 추론하기 어려움**

#### 4️⃣ Gemini가 성공한 이유

**Gemini는 이미지를 직접 보므로:**

```
👁️ Gemini가 보는 것:

[비고 셀이 시각적으로 5개 행에 걸쳐 있음]
└─ "발아 불량" 텍스트가 1)번 행 높이에 위치
└─ "직접경비" 텍스트가 첫 번째 대시 행 높이에 위치
└─ "예상수익" 텍스트가 ㆍ하위 조건들 높이에 걸쳐 있음

→ 시각적 위치 관계로 매핑 가능!
```

#### 5️⃣ Document Parse의 한계

**Document Parse가 제공하는 정보:**
```json
{
  "html": "<table>...</table>",
  "tables": [
    {
      "cells": [
        {"row": 0, "col": 2, "rowspan": 5, "content": "발아 불량은..."}
      ]
    }
  ]
}
```

**부족한 정보:**
- ❌ 병합된 셀이 **정확히 어느 내용과 의미적으로 연결**되는지
- ❌ 비고 내부의 여러 문단이 **각각 어느 조건에 매핑**되는지
- ❌ 키워드 기반 매핑을 위한 **시맨틱 힌트** 없음

## 정확도 비교

### Document Parse + Solar API 결과 (부정확)

```json
{
  "items": [
    {
      "id": "2",
      "dispute_type": "파종 후 종자불량...",
      "notes": [
        "발아 불량은...",
        "직접경비는...",
        "예상수익은..."
      ]

  ]

```
**문제:** 모든 비고가 최상위에 몽땅 들어가고, 어느 조건에 매핑되는지 구분 안됨

### Gemini Vision 결과 (정확)

```json
{
  "items": [
    {
      "id": "2",
      "dispute_type": "파종 후 종자불량...",
      "conditions": [
        {
          "condition": "재파종 가능 시",
          "notes": [
            {"keyword": "직접경비", "content": "직접경비는..."}
          ]
        },
        {
          "condition": "재파종 불가능 시",
          "sub_conditions": [
            {
              "condition": "타품종으로 재파종이 가능한 경우",
              "notes": [
                {"keyword": "예상수익", "content": "예상수익은..."}
              ]
            }
          ]
        }
      ],
      "notes": [
        {"keyword": "발아 불량", "content": "발아 불량은..."}
      ]
    }
  ]
}
```
**성공:** 각 비고가 정확한 조건에 매핑됨

## 정보 손실 비교

### Upstage Document Parse + Solar 경로

```
PDF (100% 정보)
  ↓ Document Parse
HTML (80% 정보) ← 시각적 레이아웃 손실
  ↓ Solar API
JSON (60% 정보) ← 의미적 매핑 오류
```

### Gemini Vision 직접 경로

```
PDF (100% 정보)
  ↓ 이미지 변환
Image (100% 정보) ← 시각 정보 보존
  ↓ Gemini Vision
JSON (95% 정보) ← 직접 시각 분석
```

## 각 방법의 실패 원인 요약

### 1. Azure Document Intelligence
- **무료 티어 제한**: 2페이지만 분석
- **해결책**: 유료 업그레이드 ($$$)
- **평가**: Gemini가 이미 성공했으므로 불필요

### 2. Upstage Solar DocVision
- **모델 부재**: 비전 모델이 아님
- **근본 원인**: Upstage는 멀티모달 비전 API 없음
- **평가**: 사용 불가능

### 3. Upstage Information Extraction
- **JSON 스키마 제약**: 2단계 중첩까지만 지원
- **우리 요구사항**: 5단계 중첩 구조
- **평가**: 복잡한 구조에 부적합

### 4. Document Parse + Solar API
- **HTML 변환 시 정보 손실**
  - rowspan 속성으로 구조만 보존
  - 의미적 연결 관계 손실
- **Solar API의 한계**
  - 텍스트 기반 LLM (비전 아님)
  - 시각적 공간 관계 이해 불가
  - HTML 코드만으로 병합 셀 추론 어려움
- **복잡한 매핑 실패**
  - 비고 ↔ 조건 연결이 부정확
  - 키워드 매칭에 시각적 힌트 부족
- **평가**: 단순한 표는 가능, 복잡한 표는 부정확

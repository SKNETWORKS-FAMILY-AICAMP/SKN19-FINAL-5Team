## 오류 #1: PostgreSQL 함수 Ambiguous Column 오류

### 1️⃣ 오류 원인

#### 문제 상황
- **함수명**: `public.search_hybrid_rrf`
- **에러 메시지**: `column reference "chunk_id" is ambiguous`
- **발생 위치**: `vector_results` CTE 내부 SELECT 문

#### 근본 원인
PL/pgSQL에서 `RETURNS TABLE(...)` 형태로 함수를 정의하면, 반환 테이블의 컬럼명들이 **함수 내부 변수(OUT 파라미터)** 로도 존재합니다.

```sql
RETURNS TABLE(chunk_id character varying, ...)
LANGUAGE plpgsql
```

따라서 함수 내부 SQL에서 `SELECT chunk_id`처럼 **별칭 없이 컬럼명을 사용**하면:
- **(1) 함수 반환 컬럼 변수 `chunk_id`** 인지
- **(2) 테이블 컬럼 `vector_chunks.chunk_id`** 인지

구분할 수 없어 **ambiguous column** 오류가 발생합니다.

#### 문제 코드 위치
```sql
vector_results AS (
    SELECT
        chunk_id,  -- ❌ 모호함: 함수 변수인지 테이블 컬럼인지 불명확
        (1 - (embedding <=> query_embedding))::FLOAT AS similarity,
        ROW_NUMBER() OVER (ORDER BY embedding <=> query_embedding) AS rank
    FROM vector_chunks
    WHERE
        (filter_dataset IS NULL OR dataset_type = filter_dataset)
        AND (filter_category IS NULL OR category = filter_category)
        AND (filter_document_type IS NULL OR document_type = filter_document_type)
        AND (filter_year IS NULL OR source_year = filter_year)
),
```

---

### 2️⃣ 오류 해결

#### 해결 방법
테이블에 **alias를 부여**하고, 모든 컬럼 참조를 **`alias.컬럼명`** 형태로 명시합니다.

#### ✅ 수정된 코드
```sql
vector_results AS (
    SELECT
        vc.chunk_id AS chunk_id,  -- ✅ 테이블 alias로 명확히 지정
        (1 - (vc.embedding <=> query_embedding))::FLOAT AS similarity,
        ROW_NUMBER() OVER (ORDER BY vc.embedding <=> query_embedding) AS rank
    FROM vector_chunks vc  -- ✅ alias 지정
    WHERE
        (filter_dataset IS NULL OR vc.dataset_type = filter_dataset)
        AND (filter_category IS NULL OR vc.category = filter_category)
        AND (filter_document_type IS NULL OR vc.document_type = filter_document_type)
        AND (filter_year IS NULL OR vc.source_year = filter_year)
),
```

#### 핵심 변경사항
1. `FROM vector_chunks vc` - 테이블에 alias `vc` 부여
2. 모든 컬럼 참조를 `vc.컬럼명` 형태로 변경:
   - `chunk_id` → `vc.chunk_id`
   - `embedding` → `vc.embedding`
   - `dataset_type` → `vc.dataset_type`
   - `category` → `vc.category`
   - `document_type` → `vc.document_type`
   - `source_year` → `vc.source_year`

#### 검증 방법
```sql
SELECT pg_get_functiondef(p.oid)
FROM pg_proc p
JOIN pg_namespace n ON n.oid = p.pronamespace
WHERE n.nspname = 'public' AND p.proname = 'search_hybrid_rrf';
```

## 오류 #2: Python Re-ranking 그룹화 버그

### 1️⃣ 오류 원인

#### 문제 상황
- **파일**: `03_01_search_api.py`
- **함수**: `rerank_case_chunks()`
- **증상**: PDF 데이터에서 같은 사례(`original_number`)의 청크들이 하나로 그룹화되지 않고 개별적으로 여러 번 검색 결과에 나타남

#### 근본 원인
PDF 파싱 데이터는 `source_url`이 없는데, 기존 코드는 URL이 없는 경우 **`chunk_id`로 그룹화**하도록 작성되어 있었습니다.

**문제점**:
- `chunk_id`는 각 청크마다 고유한 값 (예: `pdf_semantic_해결_2010_1_1_사건개요_1`, `pdf_semantic_해결_2010_1_1_쟁점사항_1`)
- 같은 사례(`2010_1_1`)의 청크 118개가 118개의 별도 그룹으로 나뉘어짐
- 결과적으로 검색 결과 상위 5개 중 4개가 모두 같은 사례(`2010_1_1`)로 나타남
- 각 결과가 1~2개 청크만 포함하여 문맥이 불완전함

#### 문제 코드
```python
# ❌ 버그 있는 코드 (Before)
for result in case_results:
    source_url = result.get('source_url')
    if source_url:
        url_groups[source_url].append(result)
    else:
        # URL이 없는 경우 (PDF 데이터 등) chunk_id로 그룹화
        url_groups[result['chunk_id']].append(result)  # ❌ 잘못된 그룹화!
```

#### 실제 발생한 문제 예시
**검색어**: "인터넷 쇼핑몰에서 구입한 물품에 하자가 있는 경우 환불 가능한가요?"

**버그 발생 시 검색 결과** (상위 5개):
```
1. 2010_1_1 (청크 2개) - 매트리스 무료체험 사건
2. 2010_1_1 (청크 1개) - 매트리스 무료체험 사건 (중복!)
3. 2011_2_3 (청크 3개) - 압축선반 사이즈 불일치 사건
4. 2010_1_1 (청크 1개) - 매트리스 무료체험 사건 (중복!)
5. 2010_1_1 (청크 2개) - 매트리스 무료체험 사건 (중복!)
```

→ 같은 사례가 4번 중복되어 나타나고, 각각 1~2개 청크만 포함하여 불완전한 문맥 제공

---

### 2️⃣ 오류 해결

#### 해결 방법
`original_number` 필드를 사용하여 PDF 데이터를 그룹화합니다.

그룹화 우선순위:
1. **`source_url`** (웹 크롤링 데이터)
2. **`original_number`** (PDF 파싱 데이터)
3. **`chunk_id`** (fallback)

#### ✅ 수정된 코드
```python
# ✅ 수정된 코드 (After)
for result in case_results:
    source_url = result.get('source_url')
    original_number = result.get('original_number')

    # 그룹 키 결정 우선순위:
    # 1. source_url (웹 크롤링 데이터)
    # 2. original_number (PDF 파싱 데이터)
    # 3. chunk_id (fallback)
    if source_url:
        group_key = source_url
    elif original_number:
        group_key = f"case_{original_number}"  # prefix로 구분
    else:
        group_key = result['chunk_id']

    url_groups[group_key].append(result)
```

#### 핵심 변경사항
1. `original_number` 필드를 추가로 추출
2. 그룹화 키 결정 로직을 3단계 우선순위로 변경
3. `original_number` 사용 시 `case_` prefix를 추가하여 URL과 구분

#### 수정 후 기대 결과
**검색어**: "인터넷 쇼핑몰에서 구입한 물품에 하자가 있는 경우 환불 가능한가요?"

**수정 후 검색 결과** (상위 5개):
```

2. 2011_2_3 (청크 87개) - 압축선반 사이즈 불일치 사건 [완전한 문맥]
3. 2012_3_5 (청크 65개) - 온라인 의류 구매 하자 사건 [완전한 문맥]
4. 2013_1_8 (청크 52개) - 전자제품 AS 분쟁 사건 [완전한 문맥]
```

→ 각 사례가 1번씩만 나타나고, 모든 관련 청크를 포함하여 완전한 문맥 제공

## 오류 #3: PostgreSQL 타입 불일치 오류 (NUMERIC vs FLOAT)

### 1️⃣ 오류 원인

#### 문제 상황
- **함수명**: `public.search_hybrid_rrf`
- **에러 메시지**: `Returned type numeric does not match expected type double precision in column 4`
- **발생 위치**: `search_hybrid_rrf` 함수의 반환 타입
- **보고자**: 팀원 (검색 API 테스트 중 500 Internal Server Error 발생)

#### 근본 원인
PostgreSQL은 나눗셈 연산 `1.0 / (rrf_k + b.rank)`의 결과를 **NUMERIC** 타입으로 추론합니다. 하지만 함수 선언에서는 **FLOAT(double precision)** 타입을 기대하므로 타입 불일치가 발생합니다.

**타입 추론 규칙**:
- `1.0 / (integer + integer)` → PostgreSQL은 이를 **NUMERIC**으로 계산
- `1 - (vector <=> vector)` → 벡터 거리 연산도 **NUMERIC** 반환
- `COALESCE(numeric, 0)` → **NUMERIC** 유지

하지만 함수 선언은:
```sql
RETURNS TABLE (
    ...
    rrf_score FLOAT,           -- double precision 기대
    bm25_score FLOAT,          -- double precision 기대
    vector_similarity FLOAT    -- double precision 기대
)
```

이로 인해 **타입 불일치**가 발생하여 API에서 500 에러 반환.

#### 문제 코드 위치

##### ① `vector_results` CTE (517번 라인)
```sql
vector_results AS (
    SELECT
        vc.chunk_id,
        1 - (vc.embedding <=> query_embedding) as similarity,  -- ❌ NUMERIC 타입
        ROW_NUMBER() OVER (ORDER BY vc.embedding <=> query_embedding) as rank
    FROM vector_chunks vc
    ...
)
```

##### ② `rrf_combined` CTE (532-533번 라인)
```sql
rrf_combined AS (
    SELECT
        COALESCE(b.chunk_id, v.chunk_id) as chunk_id,
        -- ❌ NUMERIC 타입으로 계산됨
        COALESCE(1.0 / (rrf_k + b.rank), 0) +
        COALESCE(1.0 / (rrf_k + v.rank), 0) as rrf_score,
        COALESCE(b.score, 0) as bm25_score,          -- ❌ NUMERIC
        COALESCE(v.similarity, 0) as vector_similarity  -- ❌ NUMERIC
    FROM bm25_results b
    FULL OUTER JOIN vector_results v ON b.chunk_id = v.chunk_id
)
```

#### 실제 오류 영향
1. **FastAPI 500 Error**: 타입 불일치로 인해 DB 함수 실행 실패
2. **NoneType 에러**: API가 None을 반환하여 Python에서 포맷팅 오류 발생
3. **검색 불가**: 모든 하이브리드 검색이 실패

---

### 2️⃣ 오류 해결

#### 해결 방법
모든 score 계산에 **명시적 `::FLOAT` 캐스팅**을 추가하여 반환 타입을 일치시킵니다.

#### ✅ 수정된 코드

##### ① `vector_results` CTE 수정
```sql
vector_results AS (
    SELECT
        vc.chunk_id,
        -- ✅ FLOAT로 명시적 캐스팅
        (1 - (vc.embedding <=> query_embedding))::FLOAT as similarity,
        ROW_NUMBER() OVER (ORDER BY vc.embedding <=> query_embedding) as rank
    FROM vector_chunks vc
    WHERE
        (filter_dataset IS NULL OR vc.dataset_type = filter_dataset)
        AND (filter_category IS NULL OR vc.category = filter_category)
        AND (filter_document_type IS NULL OR vc.document_type = filter_document_type)
        AND (filter_year IS NULL OR vc.source_year = filter_year)
    ORDER BY vc.embedding <=> query_embedding
    LIMIT 100
)
```

##### ② `rrf_combined` CTE 수정
```sql
rrf_combined AS (
    SELECT
        COALESCE(b.chunk_id, v.chunk_id) as chunk_id,
        -- ✅ RRF 점수를 FLOAT로 명시적 캐스팅
        (COALESCE(1.0 / (rrf_k + b.rank), 0) +
         COALESCE(1.0 / (rrf_k + v.rank), 0))::FLOAT as rrf_score,
        -- ✅ BM25 점수도 FLOAT로 캐스팅
        COALESCE(b.score, 0)::FLOAT as bm25_score,
        -- ✅ 벡터 유사도도 FLOAT로 캐스팅
        COALESCE(v.similarity, 0)::FLOAT as vector_similarity
    FROM bm25_results b
    FULL OUTER JOIN vector_results v ON b.chunk_id = v.chunk_id
)
```

#### 핵심 변경사항
1. **`similarity`**: `(1 - ...)::FLOAT` 로 캐스팅
2. **`rrf_score`**: 전체 계산식을 괄호로 묶고 `::FLOAT` 캐스팅
3. **`bm25_score`**: `COALESCE(b.score, 0)::FLOAT`
4. **`vector_similarity`**: `COALESCE(v.similarity, 0)::FLOAT`

- `DB/01_00_unified_schema.sql` (스키마 정의)
- `DB/migrations/fix_search_hybrid_rrf_ambiguous_column.py` (Migration 스크립트)
